## 💼 Công việc đã thực hiện

### 1. Phân tích và thiết kế nhóm API User Service ⏱️ 2.5h

- **Mô tả**:  
  Phân tích toàn bộ các endpoint hiện có của User Service và tổ chức lại theo hướng rõ ràng về **nghiệp vụ** và **mức độ truy cập**, tập trung vào authentication thay vì role-based authorization.

- **Nhóm API Authentication & Account Lifecycle (Public APIs)**:
    - `POST /api/v1/user/auth/register`: Đăng ký tài khoản mới
    - `POST /api/v1/user/auth/login`: Đăng nhập hệ thống
    - `POST /api/v1/user/auth/verify-email`: Xác thực email bằng OTP
    - `POST /api/v1/user/auth/forgot-password`: Khởi tạo quy trình quên mật khẩu
    - `POST /api/v1/user/auth/verify-forgot-password`: Xác thực OTP quên mật khẩu
    - `POST /api/v1/user/auth/reset-password`: Đặt lại mật khẩu mới

- **Nhóm API User Self-Management (Authenticated APIs)**:
    - `GET /api/v1/user/auth/secure/profile`: Lấy thông tin hồ sơ người dùng hiện tại
    - `POST /api/v1/user/auth/change-password`: Thay đổi mật khẩu
    - `PATCH /api/v1/user/auth/update-info`: Cập nhật thông tin cá nhân

- **Quyết định thiết kế quan trọng**:
    - Không triển khai role-based authorization ở giai đoạn này
    - Phân quyền dựa trên trạng thái:
        - Chưa đăng nhập (public)
        - Đã xác thực (authenticated)
    - API được thiết kế theo nguyên tắc: user chỉ thao tác trên chính tài khoản của mình

- **Kết quả**:
    - API được phân nhóm rõ ràng theo nghiệp vụ
    - Dễ mapping với frontend và các service khác
    - Tránh nhầm lẫn giữa API public và API cần xác thực

### 2. Thiết kế Authentication Flow dựa trên JWT ⏱️ 1h

- **Mô tả**:  
  Thiết kế luồng xác thực tổng thể cho User Service:
    - Người dùng đăng nhập → hệ thống xác thực thông tin
    - Cấp JWT cho các request tiếp theo
    - JWT được dùng để truy cập các API self-management

- **Định hướng thiết kế**:
    - JWT chỉ đóng vai trò xác thực người dùng
    - Không xử lý phân quyền theo role
    - Phù hợp với kiến trúc microservices và mở rộng trong tương lai

- **Kết quả**:
    - Authentication flow rõ ràng, đơn giản
    - Dễ dàng mở rộng thêm authorization khi cần

## 📚 Kiến thức học được

### 🔧 Kỹ năng kỹ thuật
- **API Design**: RESTful best practices: resource naming, HTTP methods, status codes.
- **Security**: JWT implementation details: signature algorithm (HS256), token storage, refresh token rotation.

### 💡 Khái niệm và lý thuyết
- **New Concepts**: API versioning strategies: URI path (`/api/v1/`), header (`Accept: application/vnd.api.v1+json`). Quyết định dùng URI path cho đơn giản.
- **Best Practices**: HATEOAS (Hypermedia as the Engine of Application State) - xem xét nhưng chưa áp dụng trong version 1.
- **Architecture**: Stateless authentication vs stateful (session). Microservice nên dùng stateless (JWT).

### 🤝 Soft Skills
- **Communication**: Thiết kế API như một contract - cần rõ ràng để frontend và các service khác hiểu.
- **Attention to Detail**: Chú ý đến từng field name, data type, validation rules.

## 🚧 Khó khăn và giải pháp

### Vấn đề: Phân tách ranh giới giữa API public và API cần xác thực

- **Mô tả**:  
  Trong giai đoạn thiết kế User Service, hệ thống chưa triển khai phân quyền theo role mà chỉ tập trung vào authentication. Việc xác định chính xác API nào được phép public, API nào bắt buộc phải có JWT là một thách thức, đặc biệt với các API liên quan đến tài khoản người dùng.

- **Ảnh hưởng**:  
  Nếu phân tách không rõ ràng có thể dẫn đến:
    - Public nhầm các API nhạy cảm (cập nhật thông tin, đổi mật khẩu)
    - Thiết kế API thiếu nhất quán, gây khó hiểu cho frontend và các service khác
    - Tiềm ẩn rủi ro bảo mật ngay từ giai đoạn kiến trúc

- **Nguyên nhân gốc rễ**:  
  Chưa có kinh nghiệm thực tế trong việc thiết kế ranh giới bảo mật API ở mức kiến trúc, dễ nhầm lẫn giữa nghiệp vụ “xác thực” và “quản lý tài khoản”.

- **Cách giải quyết đã áp dụng**:
    1. Phân loại toàn bộ API theo 2 nhóm rõ ràng: **public APIs** và **authenticated APIs**.
    2. Áp dụng nguyên tắc: *mọi API làm thay đổi dữ liệu người dùng đều yêu cầu xác thực*.
    3. Thiết kế các API thao tác dữ liệu theo ngữ cảnh user hiện tại (self-managed), không cho client truyền định danh người dùng.

- **Kết quả sau khi giải quyết**:
    - Ranh giới bảo mật API rõ ràng, dễ review
    - Giảm rủi ro lộ dữ liệu hoặc thao tác trái phép
    - API design nhất quán và dễ mở rộng trong các giai đoạn sau
