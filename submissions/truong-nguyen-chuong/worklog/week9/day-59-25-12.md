## 💼 Công việc đã thực hiện

### 1. Thiết kế CloudFront Distribution và Routing ⏱️ 18:00 - 19:30

- **Mô tả**: Thiết kế CloudFront distribution làm entry point duy nhất từ Internet cho toàn hệ thống. Cấu hình routing rules dựa trên path:
  - `/` và các static assets → trỏ đến S3 bucket chứa frontend (static website)
  - `/api/*` → trỏ đến API Gateway hoặc Application Load Balancer (ALB) của backend
  - Thiết lập cache policies phù hợp cho từng loại content (static vs dynamic)
- **Kết quả**: Tạo được một entry point thống nhất, giảm latency cho người dùng cuối, và ẩn toàn bộ backend infrastructure khỏi truy cập trực tiếp từ Internet.
- **Tools/Tech**: AWS CloudFront, Route 53, S3, API Gateway

### 2. Hoàn thiện Luồng Request End-to-End ⏱️ 19:30 - 20:30

- **Mô tả**: Xác định và tài liệu hóa chi tiết luồng request từ đầu đến cuối:
  - **Frontend Flow**: User → CloudFront (CDN) → S3 Bucket (Static Hosting) → Trả về HTML/CSS/JS
  - **Backend Flow**: User → CloudFront → API Gateway/ALB → ECS Services (Page Service, AIChat Service) → RDS Database
  - Xác minh tính đúng đắn của toàn bộ chuỗi xử lý, bao gồm cả security groups, VPC routing, và IAM permissions.
- **Kết quả**: Có một bản đồ kiến trúc hoàn chỉnh, hiểu rõ cách mỗi thành phần tương tác với nhau.
- **Tools/Tech**: AWS Architecture Diagram, draw.io, Lucidchart

### 3. Kiểm tra Logic và Security của Kiến trúc ⏱️ 20:30 - 21:30

- **Mô tả**: Thực hiện review security và logic cho toàn bộ kiến trúc:
  - Đảm bảo không có service nhạy cảm nào (RDS, ECS) được expose trực tiếp ra Internet.
  - Xác nhận ECS tasks chỉ có outbound traffic thông qua NAT Gateway.
  - Kiểm tra các lớp bảo mật: Security Groups, Network ACLs, IAM Roles.
  - Đánh giá tính khả dụng (high availability) và khả năng mở rộng (scalability).
- **Kết quả**: Kiến trúc tuân thủ các best practices của AWS về bảo mật và thiết kế hệ thống resilient.
- **Tools/Tech**: AWS Well-Architected Framework, Security Groups, IAM

## 🚧 Khó khăn và giải pháp

### Vấn đề: Cân nhắc giữa API Gateway và ALB trực tiếp cho routing đến backend

- **Mô tả**: Cần quyết định nên route traffic `/api/*` từ CloudFront đến API Gateway (rồi đến ALB/ECS) hay đi thẳng đến ALB. API Gateway cung cấp nhiều tính năng (rate limiting, request validation) nhưng thêm một lớp phức tạp và chi phí.
- **Ảnh hưởng**: Ảnh hưởng đến độ trễ, chi phí vận hành, và độ phức tạp của hệ thống.
- **Nguyên nhân gốc rễ**: Cần hiểu rõ yêu cầu thực tế của hệ thống (có cần các tính năng của API Gateway không?) và constraints về ngân sách.
- **Cách giải quyết đã áp dụng**:
  1. Phân tích yêu cầu: Hệ thống hiện tại chưa cần rate limiting mạnh mẽ hoặc request validation phức tạp.
  2. Ưu tiên sự đơn giản và chi phí: Quyết định route thẳng từ CloudFront đến ALB cho các API endpoints.
  3. Ghi chú rõ ràng: Trong tài liệu, ghi lại quyết định này và lý do, đồng thời đánh dấu đây là điểm có thể mở rộng sau này nếu cần.
- **Kết quả sau khi giải quyết**: Kiến trúc trở nên đơn giản hơn, dễ hiểu và dự toán chi phí rõ ràng hơn. Vẫn đảm bảo được tính bảo mật cơ bản thông qua Security Groups và ALB.
- **Bài học rút ra**: Không phải lúc nào "nhiều service" cũng tốt hơn. Thiết kế kiến trúc cần dựa trên yêu cầu thực tế và cân bằng giữa tính năng, độ phức tạp và chi phí.
